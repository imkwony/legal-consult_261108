# 법률 상담 사이트 — 설계 문서

작성일: 2026-11-08

## 1. 목적과 이유

사용자의 아버지가 개인적으로 쓸 법률 상담 챗봇 웹사이트를 만든다.

계기: 아버지가 소송을 당할 상황에 있다. 알고 싶은 것은 다음과 같다.
- 답변서를 어떻게 써야 하는지
- 변호사를 선임해야 하는지, 안 해도 되는지
- 이 소송이 어떻게 끝날 것 같은지
- 비슷한 사례가 이전에 어떻게 끝났는지(판례)

일반 AI 챗봇은 정확한 근거 없이 답한다. 이 사이트의 핵심 가치는 **국가법령정보(법제처 Open API)의 실제 법령과 판례를 근거로, 출처(조문 번호, 사건번호)를 붙여 답하는 것**이다.

사용자: 아버지 한 명(비전문가)이다. 답변은 **쉽고 명료해야** 한다. 초기 설정과 유지보수는 사용자(아들)가 한다.

## 2. 목표 / 비목표 / 실패 조건

**목표**
- 법률 MCP 도구로 실제 법령과 판례를 조회한 뒤, 그 자료를 근거로 답한다.
- 답변에 근거(법령명과 조문, 판례 사건번호, 선고일, 법원)를 표시한다.
- 상담 내용을 파일로 내려받을 수 있다.
- 상담 내용을 구글 스프레드시트에 저장하고 다시 불러올 수 있다.
- 컴퓨터와 휴대폰에서 모두 쓸 수 있다(반응형).

**비목표**
- 여러 사용자 계정, 로그인, 회원 관리
- 답변서 등 법률 문서를 완성본으로 자동 생성하는 기능(작성 요령과 구성 안내까지만 한다)
- Gemini API 직접 연결(사용자가 BAZE만 쓰기로 결정함)

**실패 조건(동작은 하더라도 실패로 본다)**
- 존재하지 않는 판례나 조문을 지어내서 근거처럼 보여준다.
- 법률 용어로 가득 차서 아버지가 이해하지 못한다.
- 사용자의 BAZE 키나 OC 키가 공개 저장소나 사이트 코드에 노출된다.

## 3. 제약

- **호스팅: GitHub Pages(정적 사이트).** 서버 코드는 없다.
- **CORS 확인 결과(2026-11-08 실측)**
  - `api.baze.co` 게이트웨이는 `Access-Control-Allow-Origin: *`이라 브라우저에서 직접 호출할 수 있다.
  - `mcp.gomdori.app/law`, `korean-law-mcp.fly.dev/mcp`, `www.law.go.kr/DRF/*`는 브라우저 Origin이 붙은 요청에 403을 주거나 CORS 헤더가 없다. 따라서 **브라우저에서 직접 호출할 수 없고, 중계가 필요하다.**
- BAZE 게이트웨이 사용량 제한: 회원당 60초에 120회, 요청 본문 최대 25MB.
- Google Apps Script 제한: 실행 1회 최대 6분, UrlFetch 일일 할당량이 있다.

## 4. 결정된 구성(사용자 결정)

### 4.1 전체 구조

```
브라우저 (GitHub Pages 정적 사이트)
  ├─→ BAZE API Gateway (AI 모델)       ← 사용자가 본인 BAZE 키를 넣은 경우 직접 호출
  └─→ Google Apps Script 웹앱 (구글 시트에 바인딩)
         ├─→ BAZE API Gateway           ← 본인 키가 없으면 소유자 키로 대리 호출
         ├─→ korean-law-mcp 원격 서버    ← OC 키 사용, MCP 도구 목록/호출 중계
         └─→ 스프레드시트                ← 상담 저장 / 목록 / 불러오기
```

### 4.2 AI: BAZE만 사용
- BAZE 문서: https://docs.factchat.kr/docs/korea-seoul/api-gateway/getting-started/overview
- Base URL: `https://api.baze.co/v1/gateway`. OpenAI 호환 Chat Completions(`/chat/completions/`)를 쓴다. 인증은 `Authorization: Bearer <키>`.
- **키 사용 규칙**
  - 설정에 본인 BAZE 키가 있으면 브라우저가 BAZE를 직접 호출한다.
  - 없으면 Apps Script가 Script Properties에 저장된 **소유자(사용자) 키**로 대신 호출한다.
- 소유자 BAZE 키와 OC 키는 **Apps Script의 Script Properties에만** 저장한다. 사이트 코드와 저장소에는 절대 넣지 않는다.

### 4.3 법률 근거: korean-law-mcp
- 저장소: https://github.com/chrisryugj/korean-law-mcp (MIT)
- 원격 엔드포인트: `https://mcp.gomdori.app/law?oc=<OC키>` (대체: `korean-law-mcp.fly.dev/mcp`)
- 사용자는 open.law.go.kr에서 OC 키를 이미 발급받았다.
- 주요 도구: `legal_research`(task 예: `full_research`, `dispute_prep`), `legal_analysis`(`verify_citations`, `cite_check`, `applicable_law`), `search_law`, `get_law_text`, `search_decisions`(`domain="precedent"`), `get_decision_text`, `discover_tools`/`execute_tool`
- Apps Script가 MCP Streamable HTTP(JSON-RPC: `initialize` → `tools/list` / `tools/call`)를 중계한다. 브라우저는 Apps Script에 "도구 목록 주세요"와 "이 도구를 이 인자로 호출해 주세요"만 요청한다.

### 4.4 답변 생성 흐름(tool calling 루프)
1. 사용자 질문과 대화 이력, MCP 도구 정의(OpenAI tools 형식으로 변환)를 모델에 보낸다.
2. 모델이 도구 호출을 요청하면 Apps Script를 거쳐 MCP를 호출하고, 결과를 모델에 돌려준다. 이것을 반복한다(상한을 둔다).
3. 모델이 최종 답변을 만든다. 답변은 조회한 자료에만 근거해야 한다(시스템 프롬프트로 강제한다).
4. 최종 답변에 인용된 판례와 조문을 `legal_analysis`(`verify_citations`)로 검증한다. 검증에 실패한 인용은 사용자에게 표시한다(예: "확인되지 않은 인용").
5. 진행 중에는 "판례 검색 중…", "민법 제○조 확인 중…" 같은 상태를 화면에 보여준다.

### 4.5 화면
- 채팅 화면 하나.
- 우측 상단에 **"설정"** 버튼을 둔다. 설정 항목:
  - Apps Script 웹앱 주소(필수)
  - 본인 BAZE 키(선택, 비워두면 소유자 키 사용)
- 설정값은 각 기기 브라우저의 localStorage에 저장한다. 휴대폰은 따로 한 번 입력해야 한다.
- 상담 **다운로드** 버튼과 **불러오기**(시트에 저장된 지난 상담 목록) 기능이 있다.

### 4.5.1 서류 입력(사용자 결정: 텍스트 또는 PDF)
- 소장 같은 서류를 **텍스트로 붙여넣거나 PDF를 올려서** 상담에 쓴다.
- **(설계자 판단)** PDF는 브라우저에서 pdf.js로 텍스트를 추출한다. 텍스트가 거의 없는 스캔 PDF(종이 소장을 스캔한 경우)는 페이지를 이미지로 바꾼 뒤, BAZE의 이미지 인식 모델로 글자를 받아 적게 한다. 추출한 원문은 대화 맥락에 넣고 상담 기록에도 저장한다.

### 4.5.2 다운로드(사용자 결정: md / Word / PDF)
- **(설계자 판단)** 다운로드 메뉴에서 세 형식 중 하나를 고른다.
  - **Markdown(.md)**: 브라우저에서 바로 생성한다.
  - **Word(.docx)**: 브라우저용 docx 라이브러리로 생성한다.
  - **PDF**: 인쇄용 스타일시트를 적용하고 브라우저의 "PDF로 저장"(인쇄) 기능을 쓴다. 한글 글꼴 문제를 피하기 위해서다.
- 파일에는 날짜, 질문과 답변, 근거 목록(조문, 사건번호), 변호사 확인 안내가 들어간다.

### 4.6 보관: 구글 스프레드시트
- Apps Script가 시트에 상담을 저장하고, 목록을 보여주고, 불러온다.
- **접속 비밀번호는 두지 않는다(사용자 결정).** Apps Script 주소를 비공개로 유지하는 것으로 보호한다. 주소는 사이트 코드에 없고 각 기기 localStorage에만 있다.

### 4.7 답변 스타일
- 쉽고 명료한 한국어로 쓴다. 결론을 먼저 말하고, 법률 용어에는 풀이를 붙인다.
- 근거를 명시한다(법령명과 조문, 사건번호, 법원, 선고일).
- 답변마다 "중요한 결정 전에는 변호사와 확인하세요" 안내를 넣는다.

### 4.8 초기 설정
- 사용자(아들)가 직접 한다. 단계별 설정 안내서(시트 생성 → 스크립트 붙여넣기 → Script Properties에 키 입력 → 웹앱 배포 → GitHub Pages 배포 → 아버지 기기 설정 입력)를 함께 제공한다.

## 5. 설계자 판단으로 정한 것(사용자 확인 전)
- 답변 하나에 20~40초가 걸려도 괜찮다고 본다(도구 호출마다 Apps Script를 거쳐 1~3초씩 걸린다).
- 진행 상태 표시와 변호사 확인 안내 문구를 넣는다.

- **(설계자 판단) MCP 원격 서버가 막히는 경우**: 대체 엔드포인트(`korean-law-mcp.fly.dev/mcp`)로 바꾼다. 그것도 막히면 Apps Script가 law.go.kr DRF API를 직접 호출하는 최소 도구(법령 검색, 조문 본문, 판례 검색, 판결문 본문)로 대체한다. 이 경우 고급 도구는 포기한다. 별도 서버는 두지 않는다.
- **(설계자 판단) BAZE가 tool calling을 지원하지 않는 경우**: 코드가 순서를 고정한 파이프라인으로 대체한다. 순서는 ① 모델이 검색어를 JSON으로 생성 → ② 코드가 `search_decisions`, `search_law` 호출 → ③ 상위 결과의 본문 조회 → ④ 그 자료로 답변 → ⑤ 인용 검증이다. Gemini 직접 연결은 다시 열지 않는다.
- **(설계자 판단) 비용**: 기본 모델은 중간 가격대 모델로 정하고, 설정에서 바꿀 수 있게 한다. 도구 결과는 길이를 잘라 넣고, 도구 호출 반복은 최대 8회로 제한한다.

## 6. 빌더에게 맡기는 것
- 프론트엔드 기술 선택(빌드가 필요 없는 순수 HTML/JS를 권장. GitHub Pages에 그대로 올리기 쉽다)
- 시트의 컬럼 구조와 저장 형식
- MCP 세션 관리, 오류 처리, 재시도
- 도구 호출 반복 상한과 결과 길이 자르기
- 시각 디자인(글자는 크고 대비는 높게. 아버지가 쓰시는 점을 고려한다)

## 7. 확인이 필요한 위험
- **BAZE의 tool calling 지원 여부**: 문서에 명시가 없다. 소유자 키로 실제 호출해 확인해야 한다.
- **BAZE 모델 목록**: `GET /v1/gateway/models/`로 확인한 뒤 기본 모델을 고른다.
- ~~korean-law-mcp 원격 서버가 서버 측 요청을 허용하는지~~ → **확인 완료(2026-11-08)**: `Origin` 헤더가 없는 POST `initialize`에는 200 OK를 준다(serverInfo `korean-law` v4.15.23). `Origin` 헤더가 붙으면 403이다. Apps Script의 UrlFetchApp은 Origin을 보내지 않으므로 중계가 가능하다. 서버의 `instructions` 필드에 도구 사용 순서 안내가 있으니 시스템 프롬프트에 포함한다.
